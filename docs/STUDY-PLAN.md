# Study paths, spaced repetition and authoring: analysis and plan

Status: D1 to D3 approved as recommended (2026-10-21). Stages 1 to 5 are built (see §4 for what changed from this proposal). Decisions
that change stored data are listed at the end.

## 1. What exists today

**Content is files, built into the app.** `content/tree/**.pgn` is one theory tree for both sides, split into chapters
(one line each, written from where it branches: `[Start "<chapter> <move>"]`). `content/courses/<id>/course.yaml` picks
the lines a course teaches, in teaching order, plus its introduction, plans and quizzes. `pnpm content:build` projects
each course into its own EPD-keyed tree (`OpeningContent`: nodes = positions, edges = moves with comments, NAGs and
arrows; variants = the course's lines) and ships it as JSON. The app never edits content. So "each course is its own
tree" is true of what the app reads, but authoring happens in one shared tree (docs/TREE.md).

**Lines and their metadata.** A line has an id (its file name), a name, ECO, kind (main, sideline, rare, gambit, or a
trap: for-us / against-us), tags (character, risk, tricks, themes), what the opponent plays to reach it, an optional
`section` (a heading on the course page), and the position that names it (`namedPly`, shown on its About tab).
Comments live on **moves** (edges), not positions. Groups are `section:` per course, and the tree index groups by first
moves; there is no free tagging of lines.

**Drilling.** Learn (both sides, every move shown), Drill (recall your moves, the computer answers), Every branch (a
random walk through the course), Quiz (spaced-repetition cards and free practice), Speed (lines against the clock, now
with a depth), Guess (name the opening), and a line's Quiz tab. Drill answers are graded and written to the same cards as
Quiz (`features/play/record.ts`).

**Spaced repetition already exists.** FSRS (ts-fsrs). A **card** is one position of one course and the move the
course plays there (`cards`: id `<course>:<epd>`, due, stability, difficulty, state new / learning / review /
relearning). `reviews` is an append-only log (rating, move played, time, hint). `cardDefinitions` decides which
positions earn cards (main and gambit lines always, sidelines unless rare in practice, rare lines by setting, never
alternatives or for-us traps, the avoiding move of against-us traps), `introductionOrder` orders them (main line first,
then other lines, each by depth), and `planIntroductions` adds up to N new cards a day (a setting) across enrolled
courses before `planSession` mixes due and new. Quizzes (typed answers) are cards too, one in about five.

**Local data.** SQLite in the browser (OPFS), one tab at a time, JSON export and import of every table (import merges
by `at` and writes nothing if any row fails). Migrations are numbered SQL files generated by drizzle-kit.

## 2. Where the brief and the code differ, and what is ambiguous

1. **A course is not its own source tree.** Lines are shared between courses and between sides. Units can still be
   per course (computed on the course's projected tree), which is what the scope rule needs.
2. **Spaced repetition is not new.** Part 3 is mostly there; the change is _what gets introduced next_ (units and
   unlocking instead of a flat order) and making a unit's progress visible.
3. **Traps and quizzes are scheduled today.** The brief calls traps "supplementary: never required, never scheduled".
   Here an against-us trap produces a card for the move that avoids it (and that move is usually on a main line
   anyway), and quizzes are scheduled cards. Needs a decision (D3).
4. **Comments are on moves, not positions.** "Comments on any position or move" would need position notes too. A move
   comment already covers "why this move"; a position note would be new.
5. **Authoring is a different architecture.** Today a course changes only when a file in the repository changes. An
   in-app editor means user-authored content in the local database, laid over the shipped content. This is the biggest
   change and touches stored data (D4).
6. **Ambiguous:** how big a unit is (proposal below); whether "passed" is a drill result or a scheduling state;
   whether units span the opponent's choices inside one of our lines (a line's side branches) or only its main path;
   whether "groups and tags" replaces `section:` or adds to it; whether a locally authored course can change a shipped
   one or only add new ones.

## 3. Proposed design

### Units (Part 1)

A pure function in core, `courseUnits(content, overrides)`, cuts a course's tree into units:

- **Main line first.** The first line's learner moves from the trigger, cut into units of about **4 learner moves**
  (one sitting), preferring cuts at branch points so a unit ends where something leaves it.
- **Then branches,** each line as one or more units of its own moves (from where it leaves the lines already in units),
  same size rule. Order: by importance, then depth: kind (main and gambit before sideline before rare), then how often
  club players reach the branch point (the popularity data the app already ships), then shallower first.
- **Dependencies:** a branch's first unit depends on the unit that contains its branch point; a line's later units
  depend on its earlier ones.
- **Core vs supplementary:** a unit is the learner's own repertoire moves on its stretch. Comments, quizzes, tags,
  for-us traps and the shown mistake of an against-us trap are attached to it and shown while studying, but never
  required.
- **Overrides** (Part 4): an author can reorder units and add or drop prerequisites. For shipped courses these live in
  `course.yaml` (`units:` overrides); for authored courses in the local database.

**State, derived rather than stored.** A unit's state comes from the cards of its positions (and the review log):

| State     | Rule (proposal)                                                                                                        |
| --------- | ---------------------------------------------------------------------------------------------------------------------- |
| locked    | a prerequisite is not passed                                                                                           |
| unlocked  | prerequisites passed, no card of the unit introduced yet                                                               |
| learning  | some cards introduced, not every move passed                                                                           |
| passed    | every core move recalled correctly, without a hint, in two consecutive answers (the last two reviews are good or easy) |
| graduated | every core card is in FSRS `review` state with an interval of 7 days or more                                           |

Deriving state keeps the database as it is (no new table, nothing to migrate, nothing to get out of step), and works
retroactively for everything already learned.

**Progress view:** a "Path" tab on the course page: the units in order, each with its state, its moves, and a button
to learn or drill it; locked units show what unlocks them.

### Sessions (Part 2)

A session type is a small object: _pick the next items from the curriculum state; record results back to cards_. A
registry makes adding one a single file. First set:

- **Next unit / next three moves:** Learn then Drill the first unlocked unit, or continue it for N moves.
- **Opening rush:** Speed, restricted to positions of passed units of this course.
- **Standard:** due reviews of this course first, then new cards from the next unlocked unit, up to the daily limit.

### Spaced repetition (Part 3)

- **Scheduler: keep FSRS.** It is already in use and in the data; it models each item's stability and difficulty, so
  it needs fewer reviews than SM-2 for the same recall, and ts-fsrs is maintained. Switching would orphan the stored
  state.
- **Granularity: one card per position and expected move, per course** (as now). A wrong move in a line drill then
  lands on exactly the position that failed (Drill already writes to that card). Line- or unit-level cards would hide
  which move was forgotten; unit state is derived from its cards instead.
- **Daily queue:** due reviews are never limited by new material; new cards come only from unlocked units in path order,
  up to the daily limit, so new learning neither crowds out reviews nor stalls.
- Supplementary items are not scheduled (subject to D3).

### Authoring (Part 4)

Recommended shape: **author in the repository's own chapter format, stored locally.** An authored chapter is the same
text as a file in `content/tree` (PGN with `[Start]`, `[For]`, `[Kind]` headers and commented moves); an authored
course is the same as a `course.yaml`. Core's tree code is pure TypeScript, so the browser can merge authored chapters
with the shipped tree exactly as the build does. Then:

- the editor is a board plus the lane tree already built: play a main line, select a pill, "Branch", play on;
- comments and supplementary tags edit the chapter's comments and headers;
- line metadata (title, description, snapshot position) and groups are headers and course entries;
- what is published (Part 5) is literally what would go in the repository;
- data safety: every save keeps the previous version (append-only history, so undo and "restore" are a row away);
  deletes are soft until confirmed; the existing export includes authored content; a reminder to export appears after
  a number of edits or days without an export.

### Publishing (Part 5)

- **Format: YAML, with each line's moves as PGN inside it.** One document per contribution: the course entry (id,
  name, side, trigger, introduction) and the chapters, each with its headers and movetext. YAML over JSON because
  it is far easier to read in a review (block text, no quoting of every string) and it is already the repository's
  format for courses; PGN for the moves because any chess tool and Lichess can read it, so a reviewer can paste it into a
  board. The app reads it back with the same parsers, and an accepted contribution becomes files in `content/`.
- **Feasibility:** a purely local app cannot create an issue through the GitHub API without the user's token (and
  storing one is a security burden). It can open
  `https://github.com/njtwomey/knightschool/issues/new?template=contribution.yml&title=…&body=…` in a new tab, with
  the user signed in to GitHub. URLs much over about 8 KB are refused, which is a few lines' worth. So:
  - small contributions: a pre-filled new-issue link (with an issue form template that labels it);
  - larger ones: copy the YAML to the clipboard and open the blank form with a note to paste, plus a "download the
    file" option to attach it (GitHub accepts .txt attachments);
  - both need a GitHub account. I recommend this; it is not fragile, because the fallback always works.

## 4. Stages

Each stage stands on its own and is small enough to review.

1. **Units and the Path view.** `courseUnits` in core with tests, unit state derived from cards, a Path tab per course
   with learn and drill per unit. No data change. **Done.** As built, differing from §3:
   - Units cover branches inside a line's file too (its side variations), not only lines' main paths: more than half of
     the cards are in them. A branch inside a file belongs to that line.
   - Branches of half a unit or less (one or two learner moves) leaving the same unit, of the same importance, are grouped
     into one "other replies" unit with a short stretch each, played one after another; otherwise a course like the
     Caro-Kann was 90 one-move units out of 140.
   - "Popularity at the branch point" is the popularity of the position the branch leads to, so branches from the same
     point are ordered by how often each is met.
   - Passed counts a move graduated on its own (a single easy answer can put it at a week) as passed.
   - Traps attach to the unit they leave from; quizzes to the unit reaching their position, else to their trap's unit.
   - The path is cut with the learner's card settings (rare lines, popularity cut), so it matches the cards.
   - `/play/<course>/<line>/<learn|drill>/<n>[/<first>-<last>]` plays one unit (or some of its moves); one new read
     query, `reviews.byOpening`, and no schema change.
2. **Sessions from the path.** "Next unit", "next three moves", "opening rush" on top of Learn, Drill and Speed, through a
   small session registry. No data change. **Done**, on the Path tab (`features/path/sessions`, one file per type).
   Next unit learns the first ready unit, or drills the one being learned (Learn ends with "Now drill it"). Next three
   moves takes the current unit from its first move not yet passed: drilled, or learned when none of those moves is in
   the quiz yet. Opening rush is Speed with a new source, `rush:<course>`: each passed unit from the first move to its
   end (the depth choice does not apply), repeated to fill the run when few are passed. "Standard" is stage 3.
3. **Path-ordered introductions.** New cards come from unlocked units in path order; the daily queue stays as it is.
   Supplementary items stop being cards if D3 says so (a data change: see below). **Done**, with no data change:
   `planIntroductions` (now in `units.ts`) takes each course's cards and reviews and offers the cards of unlocked units
   and units being learned, in path order, taking turns between courses, up to the daily limit. Quizzes are no longer
   introduced; quiz cards already stored stay and are still asked when due (nothing is deleted). Due reviews always come
   first (`planSession`, unchanged). Learn and Drill in `features/play/record.ts` are unchanged: what you choose to
   learn or drill makes its cards whatever the path says, so jumping ahead still works. Free practice and the build's
   card counts keep the flat `introductionOrder`.
4. **Unit order overrides for shipped courses** in `course.yaml`, checked by the build. **Done**: `units:` with `order`
   (these units first, as early as their prerequisites allow), `after` (more prerequisites) and `drop` (fewer), by unit
   id. The build checks the ids against the units of the default card settings and rejects an unknown id, a cycle and
   an impossible order, naming the file. In the app, where the learner's settings may cut other units, entries naming
   units that do not exist are ignored, and if what is left fails the default path is kept. No course uses it yet.
5. **Authoring, local storage.** Tables for authored chapters and courses with history; merge into the tree at load;
   export and import them; reminders. (D4.) **Done** (D4 and D5 approved): migration 5 adds `authored_chapters`,
   `authored_courses` and `authored_history` and touches nothing else (tested by upgrading a schema-4 database and
   importing a schema-4 export). History rows hold the item as it was before each change, grouped by action; undo takes
   back the newest action and is itself recorded; deletes are soft. The browser merges the authored chapters with the
   shipped ones (the build now also writes `chapters.json`, the chapters as written) with `resolveTree` and
   `projectCourse`, so an authored course shows on Courses, its Path tab, Learn, Drill, Quiz and the tree. Decisions
   made here: authored courses are new courses (a shipped course cannot be edited locally, but an authored chapter can
   branch from a shipped one with `[Start]`); the one-comment-per-move rule applies, so an authored move cannot
   comment differently on a move the shipped tree already explains (the chapter is left out with the reason); board
   search leaves authored lines out. Move comments stay on moves (no position notes): a move's comment describes the
   position it leads to. Supplementary tags are a PGN command in the comment, `[%tag tip,trap]`, carried to
   `Annotation.tags`. Line metadata is in the headers: `[Variation]` the title, a new `[Description]`, and `[Snapshot]`
   (a ply; authored lines without one are pictured at their end). The export reminder comes after 20 authored edits or
   7 days since the last export.
6. **The editor,** under Profile (a new tab beside Overview, Stats and Settings, e.g. `/profile/author`, and an entry in
   the profile menu): board, lane tree, branch, comment, tags, metadata, groups, overrides, undo.
7. **Publishing:** YAML serialisation and reading, issue form template, link, clipboard and download fallback.

## 5. Decisions needed before building (hard to reverse)

- **D1, unit state stored or derived.** Recommended: derived from cards and reviews (no schema change). Storing it
  would add a table that has to be kept in step with cards.
- **D2, unit size and order.** Recommended: about 4 learner moves; branches ordered by kind, then popularity, then
  depth. Changing it later only moves where units start; no data depends on it if D1 is derived.
- **D3, traps and quizzes.** Keep the avoiding move of an against-us trap as a card (it is a real move you must play)
  but make the trap line itself supplementary; and make quizzes supplementary (shown in study, not scheduled), or keep
  them scheduled. Unscheduling quizzes would leave existing quiz cards unused (they would stay in the database but not
  be asked).
- **D4, authored content in the local database.** New tables (chapters, courses, history), a migration, and an export
  format version bump. Before this, the app's stored data is only progress; after it, it holds work that cannot be
  rebuilt from the repository, so the backup reminder matters.
- **D5, publishing.** Pre-filled issue link with clipboard and download fallback, and an issue form template in
  `.github/ISSUE_TEMPLATE/`.
- **Related, from docs/TREE.md:** cards are still per course, so a line shared by two courses is learned twice. Keying
  cards by position and answer (one migration) would share progress across courses. Not needed for this brief (its
  scope is one course), so I suggest leaving it.
